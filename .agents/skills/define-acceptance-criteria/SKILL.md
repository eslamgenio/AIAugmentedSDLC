# Define acceptance criteria

Use the analyzed requirements and any supplied scope decisions, source evidence, and existing criteria. Work from the specific revisions provided. Produce the A04 Markdown acceptance criteria artifact for A05 requirements review. Use A03 analyzed requirements; consult A01 elicitation and supplied E01/E02/E03 human decisions for evidence and unresolved intent. Preserve the input artifacts.

1. **Establish what can be specified.** Retain every input requirement ID (`RQ-###` when available), source ID (`SRC-###`), and question ID (`Q-###`). Use the analysis handoff eligibility list when present. Write criteria only for confirmed, ready, in-scope obligations; precise but unapproved proposals are not eligible. Keep in-scope, undecided, deferred, and out-of-scope items distinct. If an input has no stable requirement ID, assign a clearly marked provisional ID and preserve its source locator. If an existing criterion already covers the same observable obligation, reuse its `AC-###` ID. Allocate unused IDs for new obligations; mark replaced criteria as superseded and link replacements instead of reusing their IDs for different obligations.
2. **Translate obligations to observable checks.** Write Given/When/Then, with a precondition or actor, a single trigger, and a result someone can observe. Split independent obligations; combine linked observations when both are necessary to distinguish success from failure. Express each criterion in terms of product behavior, not an implementation mechanism unless the source requires it. Cover the normal outcome and any distinct failure, permission, side-effect, boundary, or state transition implied by the evidence. For a specified threshold, include the exact threshold and adjacent representable cases when useful; preserve units, comparison direction, precision, and inclusivity. For a specified quality target, retain measurement conditions and success threshold. Do not generate exhaustive test cases or scenarios unrelated to acceptance.
3. **Do not settle ambiguities by writing them into checks.** Never invent a threshold, error status, role, default, timing window, retry policy, or side effect. If interpretations disagree, the outcome is unspecified, or a source is unavailable, record the exact decision needed and the affected requirement IDs. Cite the existing question ID or add a clearly labeled proposed question. Write independently supported criteria for unaffected obligations; mark the requirement `Partial` when any of its acceptance obligations remain unresolved. Do not turn a hypothetical alternative into an acceptance criterion or silently narrow scope.
4. **Reconcile coverage.** List every input requirement in the coverage table, mapping it to valid criteria and/or an explicit reason no criterion was written. Check that each criterion has a requirement and source locator, that each result can be checked, and that no blocked or excluded obligation was treated as ready. Keep approved acceptance separate from criteria readiness; the skill does not grant approval.

## A04 Markdown artifact and review handoff

Read and use the repository-root-relative [A04 template](../../../AIAugmentation/templates/A04_acceptance-criteria-outputs.md), at `AIAugmentation/templates/A04_acceptance-criteria-outputs.md`, before writing the artifact. Preserve its headings and catalog field names; fill applicable sections and explicitly mark empty or unknown content. If the template is unavailable, provide a draft inline and name the missing path rather than claiming a canonical artifact.

Write an actual Markdown file named `A04_acceptance-criteria-outputs_{iteration_id}_v{artifact_version}.md` in the requested or established artifact location. Use the iteration and version supplied by the project or user. If naming metadata or a writable destination is unavailable, return the Markdown draft inline and say what prevents saving; do not invent metadata or claim a save. Do not overwrite prior versions without authorization.

Start the artifact with YAML frontmatter delimited by `---` and these nine keys: `artifact_id`, `schema_version`, `artifact_version`, `producer_or_owner`, `iteration_id`, `created_at`, `source_artifact_versions`, `status`, `evidence_refs`. Use verified project values only. Preserve exact source revisions and source IDs or locators; use actual creation time if known. Keep `source_artifact_versions` and `evidence_refs` as YAML lists, using `[]` only when verified entries are unavailable. Represent unknown scalar values as YAML `null` only when allowed by the project. The artifact's status is neither human approval nor a claim about readiness.

After frontmatter, use the template’s ordinary Markdown sections and place the following guidance in its corresponding sections:

- **Source references / basis:** input revision(s) or source labels, confirmed scope, and any source limitations.
- **Required content and A04-01 / A04-02:** one row per check with `ac_id`, `req_id` (one primary requirement), `precondition`, `action`, and `expected` (Given, When, Then). Retain `evidence_ids` or source locators, and add kind (normal, negative, boundary, transition, or quality) where helpful.
- **Coverage:** `Requirement | Criteria | Status | Gap or reason`. Use `Specified` for fully traceable observable criteria, `Partial` for a mix of specified and unresolved obligations, `Blocked` when no obligation can safely be specified, and `Excluded` or `Deferred` where explicit scope says so. Show any affected question IDs.
- **A04-03 / boundary questions:** preserve `boundary_questions` as a table of `question_id | req_ids | decision_needed | evidence_ids or source locator`. Do not collapse materially different choices into one question. If none, say so.

In **Child Artifact Register**, use the columns `Child ID | Version | Location` and retain A04-01, A04-02 and A04-03. For an embedded child, use the parent artifact version and the exact existing section anchor (`#a04-01`, `#a04-02`, or `#a04-03`). For a separately stored child, use its verified version and actual path relative to the parent artifact; verify the path resolves and never copy or rename native evidence just to populate the table. Record `Unknown` for any unverified version or location; do not invent one or misrepresent a missing child as embedded.

If explicitly supplied, read legacy JSON inputs as evidence without modifying or converting them. Do not emit a JSON artifact or embed a JSON payload in the new Markdown artifact.
